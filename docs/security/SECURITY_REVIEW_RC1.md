# Security review — RC1 (P5.2)

- **Scope:** commit `b821c77` (ADR-002 accepted, not yet implemented in code). `apps/api`,
  `apps/web`, `apps/shop-agent`, `packages/shared`, `infra/`, Dockerfiles.
- **Method:** manual code review against the P5.2 checklist and CLAUDE.md invariants. Every finding
  below was verified in code at the cited lines. No running server was used.
- **Reviewer:** Claude (automated review agent), 2026-11-10.

## Summary

The core design holds up: device tokens are SHA-256-hashed server-side and DPAPI-protected on
Windows, shop/device queries are consistently scoped by the device-derived `shopId` (central
`shop-scope.ts`, cross-tenant → 404), staff passwords use Argon2id with timing equalisation, the
production boot guard refuses demo payments/OTP, webhooks are verified over the raw body with a
constant-time compare, PDFs are validated by content, and both dependency audits are clean.

There are **3 high** findings that block "Done when: no open high/critical findings":

1. The demo stack forces **committed S3 credentials** on an S3 endpoint that must be reachable
   from the internet, so anyone with the repo can read every customer PDF (H1).
2. The **placeholder-secret guard** misses the demo template's `CHANGE-me…` values (case-sensitive
   regex) and does not run at all in `APP_ENV=demo` (H2).
3. **`/shop/jobs/:id/resolve` (REPRINT / MARK_FAILED → refund) and `PATCH /shop/mode` do not
   require an operator session**, contrary to the contract and invariant 8 (H3).

Medium items: no security headers (Helmet/HSTS/CSP/frame-ancestors) on API or web, operator and
tracking tokens written to request logs, no `trust proxy` (per-IP limits collapse to one global
bucket behind the planned reverse proxy), and retention never deletes files of
`READY_FOR_PICKUP` orders (which becomes the normal end state under ADR-002).

## ADR-002 (daily pickup number) — review notes

ADR-002 is accepted but not implemented at `b821c77` (there is no daily-number column or code yet;
`verifyPickup` still uses the HMAC code, scoped by the device's shop at
`shop-jobs.service.ts:293-297`). Guessable numbers are an accepted risk and not reported. For the
implementation, these conditions keep the number from leaking cross-tenant data or being used to
read orders:

1. **Never a lookup key on customer or public endpoints.** Customers reach orders only via
   `TrackingGuard` (tracking token or owning session). Don't add any `GET …?pickupNumber=`/`/orders/by-number`
   route, and don't index socket rooms by number.
2. **Shop-side lookups must be scoped** by the device's `shopId` **and** the business date
   (`where: { shopId: device.shopId, businessDate, pickupNumber }`). Uniqueness:
   `@@unique([shopId, businessDate, pickupNumber])`. Shop A's #7 must 404 from shop B's device.
3. **Assign inside the paid transition's DB transaction** (e.g. `SELECT … FOR UPDATE` on a per-shop
   daily counter row, or `MAX()+1` guarded by the unique constraint with retry). Never compute it in
   the client or the agent.
4. **Customer view:** return the number only to the order's authenticated viewer (`toPublicOrder`),
   with the date; the `/customer` socket hint must stay ids + status only (`realtime-mapping.ts:30`).
5. **Retention** must count from `readyAt` (see M4), since no `COLLECTED` transition will exist.
6. **Retiring the old machinery:** when `POST /shop/pickups/verify` is removed, also drop
   `PICKUP_CODE_PEPPER`/`PICKUP_CODE_ENC_KEY` from the required config, or keep them under the H2
   placeholder checks while they still exist.
